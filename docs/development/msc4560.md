# Experimental MSC4560 stripped-state queries

Build with `cargo build --features unstable-msc4560`, then set the top-level
configuration option `enable_stripped_state = true`. The default is disabled.
Enabling the option in a binary without the Cargo feature is a configuration
error. `/versions` advertises `org.continuwuity.msc4560` only with both enabled.
These are experimental paths, not a claim of support in a published Matrix
version. The implementation follows [MSC4560](https://github.com/matrix-org/matrix-spec-proposals/pull/4560),
reviewed on 2026-11-17; the protocol models are based on
[Ruma's implementation](https://github.com/ruma/ruma/commit/19e6bf50dcc133d9becb1830e335e73e8f3f3c66).

## Requests and responses

- Client POST:
  `/_matrix/client/unstable/org.continuwuity.msc4560.stripped_state/{room_id_or_alias}`.
  Authentication is optional. Supplied access tokens use the normal
  local/appservice/OAuth policy; invalid credentials never become anonymous.
- Federation POST:
  `/_matrix/federation/unstable/org.continuwuity.msc4560.stripped_state/{room_id}`.
  Authentication is optional. Supplied X-Matrix signatures are verified normally;
  invalid signatures or other authentication schemes are rejected. Bearer tokens
  are not federation authentication for this endpoint.
- Both bodies default to `{"state": [], "num_joined_members": false}`. State
  types select every state key, including nonempty space-relation keys. Empty and
  count-only queries still require authorization.
- The eleven-type allowlist includes create/name/avatar/topic/join-rules,
  canonical-alias/guest-access/history-visibility/encryption, and space child/parent.
  Forbidden or unknown types return `M_INVALID_PARAM` before alias/network lookup.
- More than 32 original `via` entries returns HTTP 400 `M_TOO_LARGE`, including duplicates.
  Valid entries are subsequently deduplicated. This follows the proposal rather
  than the error-code comment in Ruma's referenced source.
- Every response contains `state`. Counts are queried/returned only on request;
  zero remains meaningful. Only client responses have `via`, naming the
  actual supplying server. Received state is preview data and is never persisted.

Registered local aliases resolve from the local directory. Remote aliases use a
signed directory lookup at the alias's authoritative server. Explicit vias take
precedence; returned alias candidates fill remaining slots up to 32. Unknown
on-demand application-service aliases must first be registered through the
existing alias APIs.

## Visibility and trust

Local residency requires this server's current joined-room projection; retained
outlier/state data alone is insufficient. A resident server's local decision is
authoritative, including denial; a supplied via cannot bypass it. A room lock
protects the captured current frame while authorizing and selecting state. Only
selected event IDs/bodies are fetched; member bodies are not exported.

Local client access allows world-readable history, joined/invited users,
public/knock/knock-restricted join rules, or a verified room-membership allow rule
for a restricted room. Other access is denied. Restricted allow rules retain
Matrix's [alternative-room semantics](https://spec.matrix.org/v1.19/server-server-api/#restricted-rooms):
a matching allowed membership suffices.

Signed federation callers are checked against the room ACL before any public
visibility allowance. A server with joined users, or satisfying a restricted
room's membership condition, may access the preview. Other signed callers and
unsigned callers use anonymous visibility. An unsigned request has no invented
server origin. Optional federation authentication differs from the required
signature metadata in Ruma's referenced implementation.

A peer can falsify a preview: the state cannot be authenticated as the room's
actual current state without joining. Clients should display the supplying
`via`. Peer responses are checked for requested types, duplicate keys, valid
senders, object contents and requested counts. Serialization rebuilds only
`type`, `state_key`, `sender` and `content`; PDU metadata and a forged `via`
are discarded. Client credentials are never forwarded to peers.

## Operational bounds

- A separate per-IP bucket uses the configured `rc_message` rate/burst settings
  before authentication, including trusted-proxy address handling. Eight
  admitted requests share the client/federation paths; capacity exhaustion
  returns HTTP 503 rather than creating a waiting queue.
- Request JSON is capped at 16 KiB before signature verification/body parsing.
  Credential validation has a two-second deadline, including external key or
  OAuth lookup; expiration returns 503 without downgrading authentication.
- At most four stripped-state peers run concurrently. Each peer has a two-second
  deadline covering discovery, request and response reading. All supplied unique
  candidates are attempted before a terminal error, unless one succeeds.
- Remote alias lookup has a two-second deadline and a 64 KiB response cap.
  Normal federation destination, DNS/IP, redirect and allow/deny policy applies.
- Responses are capped at 512 KiB and 1,024 selected state events. Oversized local
  selections fail instead of truncating; oversized/malformed peer responses count
  as failed candidates. Both fixed-length and streaming bodies are bounded.
- Failed or unreachable peers produce `M_NOT_FOUND` if no candidate succeeds.
  Federation queries never proxy unknown/nonresident rooms onward.

Native PostgreSQL HTTP regressions exercise local/alias queries, private and
restricted visibility, counts, credential rejection, actual signed federation
requests, ACLs, input limits and disabled behavior. Unit tests exercise malicious
PDU stripping, duplicate/unrequested data and oversized incomplete HTTP bodies.
The separate `MSC4560 stripped-state federation` CI job builds the feature,
enables the runtime option, and queries public/private rooms and aliases across
two real Palpo containers, including a successful via after five failed peers.
