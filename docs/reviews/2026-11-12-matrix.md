## 总体判断

项目已有较广的路由、事件授权、状态解析、密钥、联邦以及同步实现，不能简单归类为原型。`docs/protocol-capabilities.md` 对稳定版本、实验特性、编译门控与测试证据的区别交代较清楚，混合联邦测试清单也覆盖多个实际互操作方向。但稳定契约仍有可定位的基础缺口，尤其是 OpenID、完整状态同步和过滤器语义。当前没有足够证据给出“Matrix 完成度百分比”；版本列表、路由存在、历史通过数量与协议语义覆盖是不同指标。

建议将以下可确认缺陷先于增加 MSC 广告和新接口处理。

## 可确认发现

### MX-01 / P1：OpenID userinfo 被错误地纳入普通用户令牌或联邦签名认证

- 位置：`crates/server/src/routing/federation.rs:39,45,57`；`crates/server/src/hoops/auth.rs:28`；`crates/server/src/auth.rs:67`；`crates/server/src/routing/federation/openid.rs:11`。
- 证据链：userinfo 挂在 `authenticated_router()` 下。标准请求的 `access_token` 查询参数被 `AuthArgs::uses_access_token()` 识别为普通 Matrix access token，随后先查询用户设备令牌、appservice 令牌或 delegated introspection。真正的 OpenID 查询逻辑在 handler 内，无法先执行。`routing/client/user/openid.rs:44` 将生成的令牌写入独立的 `user_openid_tokens` 表，不会赋予它普通用户 access token 身份。
- 触发：用户通过客户端接口取得 OpenID 令牌，第三方服务仅携带该令牌 GET `/_matrix/federation/v1/openid/userinfo?access_token=...`。
- 影响：标准身份验证交换失败；用户可能能生成令牌，却无法让 widget/第三方服务验证身份。这是已实现功能的接线错误，不是可选功能未实现。
- 规范：[Matrix v1.12 OpenID](https://spec.matrix.org/v1.12/server-server-api/#get_matrixfederationv1openiduserinfo) 将此接口定义为无需额外认证，令牌自身只用于 OpenID。
- 修复：将 userinfo 挂到不经过通用认证的路由，由 handler 校验 OpenID 令牌及过期时间；另行明确 federation 全局关闭时的产品政策。
- 验收：真实申请令牌→无 Authorization 的 userinfo 返回 `sub`；未知/过期令牌返回规范错误；普通 Matrix 令牌不能替代 OpenID 令牌。置信度：高，未实发 HTTP。

### MX-02 / P1：`/sync?full_state=true` 被多个增量优化分支跳过

- 位置：`crates/server/src/sync_v3.rs:92`、`:603`、`:723`。
- 证据链：正常同步的 next_batch 为 `curr_sn + 1`（`:121`）。无新位置时，下一请求可在 `since > curr_sn` 分支直接返回空响应，此分支未检查 `full_state`。即使绕过它，`load_joined_room()` 在空 timeline 且 frame 未变化时直接返回空状态；有 timeline 而 frame 未变化时，`if since_frame_id != current_frame_id` 仍挡住 `full_state`，内层的 `if full_state || changed` 无法补救。
- 触发：先完成同步，在房间无状态变化时带上该 since 和 `full_state=true` 再请求；或期间仅产生普通消息。
- 影响：客户端要求重新取得完整状态以修复本地缓存时仍收到增量/空状态，房间可能被整体省略。
- 规范：[Matrix v1.12 sync](https://spec.matrix.org/v1.12/client-server-api/#get_matrixclientv3sync) 要求 full_state 即使有 since 也返回完整状态，同时保留 timeline 的 since 边界。
- 修复：让 full_state 进入显式完整状态路径，越过 idle-token 和 unchanged-frame 优化；保持过滤器与 lazy-load 的规范边界。
- 验收：无新事件、仅消息变化、状态变化三种情况，均比较 `full_state=true` 和初始完整状态；另测过滤后的空 timeline。置信度：高，未实发 HTTP。

### MX-03 / P2：房间事件类型过滤没有通配符，空白名单在 SQL 与内存中也不一致

- 位置：`crates/server/src/event/pdu.rs:978,998`；`crates/server/src/room/timeline/stream.rs:197-216`；`crates/server/src/room/timeline/topolo.rs:307-326`。
- 证据链：`PduEvent::can_pass_filter()` 使用字符串 contains，SQL 使用 `eq_any/ne_all`，均将 `m.room.*` 当字面量。SQL 还在 `types/senders/rooms` 为空 Vec 时跳过限制，而 PDU 内存过滤把 `Some([])` 视为不匹配任何事件。全局事件过滤 `sync_v3.rs:52` 已使用 `event_type_matches`，同一请求里的不同 section 因而语义不同。
- 触发：`room.state.types=["m.room.*"]`、`room.timeline.not_types=["m.room.*"]`，或 `room.timeline.types=[]`。
- 影响：合法白名单丢失预期事件，黑名单无法排除匹配事件；空白名单意外返回全部 timeline。影响 /sync 以及复用这些读取器的 /messages 等路径。
- 规范：[Matrix v1.12 Filtering](https://spec.matrix.org/v1.12/client-server-api/#filtering) 为 types/not_types 定义星号通配符；缺失列表与提供空列表应分开处理。
- 修复：统一过滤语义，尽可能在数据库正确实现模式匹配，并正确转义 SQL 模式元字符；避免“先 limit 再内存过滤”造成页大小和游标错误。复用或对齐已有 `event_type_matches` 的行为。
- 验收：精确类型、前/中/后缀星号、全星号、正负名单冲突、空名单、缺失名单，在初始/增量 sync、state、历史/实时分页中结果一致。置信度：高。

### MX-04 / P2：房间 account_data 和 ephemeral 的 section 过滤器未应用

- 位置：`crates/server/src/sync_v3.rs:849-870`、`:886`、`:926`。
- 证据链：读取 receipt、typing 后直接装入 `edus`，读取房间 account data 后只转换枚举便 collect。当前文件无 `filter.room.ephemeral` 或 `filter.room.account_data` 的应用点；父级 room 过滤不能替代 section 过滤。
- 触发：已加入房间，设置 `room.ephemeral.types=[]` 或 `room.account_data.not_types=["m.tag"]` 后产生对应更新。
- 影响：返回用户明确排除的 section 内容，浪费流量和解码成本，并使依赖过滤器进行独立同步的客户端行为不一致。此处是同一已授权用户收到自身数据，不能据此宣称跨用户信息泄漏。
- 修复：分别对 account_data、ephemeral 应用 types/not_types、rooms/not_rooms 以及适用的 sender/limit 语义；receipt 复合事件的 sender 语义需按规范处理，不能只看顶层字段。
- 验收：section 空白名单、排除 typing/receipt、排除 m.tag、自定义 account data、父级与子级房间过滤交叉。置信度：高。规范依据仍为上述 Filtering；本项基于代码缺少应用路径。

### MX-05 / P1：left-room 加载错误被吞掉后仍推进全局同步游标

- 位置：`crates/server/src/sync_v3.rs:233-267`、`:415-416`；`:1101-1102` 还将读取当前 frame 的所有错误转为空 LeftRoom。
- 证据链：`load_left_room()` 失败时仅日志后 continue；成功响应的 next_batch 仍为原先捕获的 curr_sn+1。下次请求若 since 大于该离开事件的 publication，`:244` 跳过该房间，因此普通增量同步没有重试机会。
- 触发：某房间的离开事件已发布，构造该房间同步内容时发生短暂数据库/状态加载错误；其他部分可正常构造。
- 影响：客户端可能永久漏收 leave/kick 通知，持续保留“已加入”显示；日志中的错误无法修复客户端已确认的游标。具体触发概率需故障注入测量。
- 修复：传播无法区分为“确实不存在”的错误，使客户端从原 since 重试；或为失败房间建立可证明不会丢失的独立重试/游标机制。不要用空成功掩盖数据库故障。
- 验收：为 left-room 状态/timeline 读取注入一次失败；失败响应不得确认新游标，恢复后使用相同 since 必须收到离开信息。置信度：高（故障条件推导，未做注入）。

### MX-06 / P2：未提供 timeout 的空 `/sync` 默认等待 30 秒

- 位置：`crates/server/src/routing/client/sync_v3.rs:74-76`。
- 证据链：空响应时 `args.timeout.unwrap_or(Duration::from_secs(30))`，然后实际等待 watcher。
- 触发：带有效 since、当前无新数据的请求省略 timeout 参数。
- 影响：要求立即完成的一次性同步请求被额外挂起约 30 秒，影响调用链超时与客户端探测。明确传 timeout 的长轮询不属于此问题。
- 规范：[Matrix v1.12 sync](https://spec.matrix.org/v1.12/client-server-api/#get_matrixclientv3sync) 将未提供 timeout 的默认值定义为 0。
- 修复：默认 0；服务端最大值仍可保留 30 秒。避免为 timeout=0 创建不必要的 watcher。
- 验收：省略 timeout、timeout=0、较短正值及超上限正值，分别检查返回行为。置信度：高。
