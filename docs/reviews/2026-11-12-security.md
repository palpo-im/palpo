# 安全性专项评审（2026-11-12）

基线：`61b2ad7f02e216e6292116abfa3bcdd8e85cae25`。静态代码审查；没有对运行中的实例攻击、没有运行数据库集成测试或 Docker 构建。下述“确认”指完整数据流中的实现缺陷已确认，不代表已进行线上利用。优先级 P1 为应优先修复的隐私/认证边界问题，P2 为有条件的资源保护缺口。

## SEC-01 / P1：私有已读回执被发送给其他房间成员（确认，置信度高）

- 写入：`crates/server/src/routing/client/room/receipt.rs:80` 调用 `set_private_read`；`crates/data/src/room/receipt.rs:83` 将类型保存为 `m.read.private`。
- 泄露源：`crates/data/src/room/receipt.rs:17` 的 `read_receipts` 仅按序号和房间过滤（23–27），没有 viewer 参数；61 行保留原始 ReceiptType，生成所有用户的私有回执。
- 对外输出：`crates/server/src/sync_v3.rs:850` 直接将整个结果发送到当前同步用户的 ephemeral；`crates/server/src/sync_v5.rs:1398` 同样调用该函数，仅过滤被忽略用户，不过滤其他人的 private 类型。
- 触发：A、B 同房间；B 取得同步游标；A 发送 `m.read.private`；B 再同步。B 可以读到 A 的事件定位和私有回执，破坏隐藏已读状态的隐私承诺。增量查询本身就足以触发，不依赖猜测事件 ID。
- 规范：[Matrix private read receipts](https://spec.matrix.org/v1.13/client-server-api/#private-read-receipts) 明确禁止向其他用户发送该回执。
- 建议：让数据访问层显式接收 viewer，以 `ty != m.read.private OR user_id = viewer` 过滤。核查 v3/v5/private 额外拼装是否重复；联邦 EDU 路径也使用同一“可公开回执”边界。
- 验收：双用户双设备集成测试；B 的 v3 和 sliding sync 均无 A 的 private 项；A 的其他设备仍可收到；公开回执和 threaded receipt 正常。

## SEC-02 / P1：刷新返回的访问令牌有效期未落实，绝对会话期限持续延长（确认，置信度高）

- `crates/server/src/routing/client/session.rs:1170` 返回 access token 的 `expires_in_ms`。
- 实际写入：`crates/data/src/user/device.rs:529` 使用 `NewDbAccessToken::new`，而 `crates/data/src/user/access_token.rs:58` 固定 `expires_at: None`；更新时仅替换 token（device.rs:538），没有赋予有效期。
- 鉴权：`crates/data/src/user/access_token.rs:156` 的数据库/缓存路径都未检查过期时间；缓存只按缓存驻留时间判断新鲜度（90–98），TokenAuth 也不保留到期时间。
- 绝对会话期限：`crates/server/src/user.rs:314` 的 `valid_refresh_token` 只读取/检查 refresh expires_at；不读 ultimate_session_expires_at。`session.rs:1147` 每次刷新重设 `now + session_ttl`。
- 影响：刷新后响应声称会过期的访问令牌可在有效期后继续调用 API，直至主动轮换/撤销；窃取的访问令牌的可用窗口超过协议承诺。拥有 refresh token 且持续刷新的会话不受原始绝对期限限制。
- 精确边界：`set_access_token` 会按 user/device 替换旧 token 并失效本进程缓存，因此本评审**不声称**旧 token 在成功轮换后仍有效。登录响应 `expires_in: None` 本身允许非过期 token；问题是 refresh 响应与实际行为不一致。
- [Matrix refresh endpoint](https://spec.matrix.org/v1.19/client-server-api/#post_matrixclientv3refresh) 定义 expires_in_ms 为访问令牌寿命。
- 建议：分离 access/refresh/absolute expiry，持久化 access expiry，并在每次鉴权（含缓存命中）检查；轮换沿用原始 absolute expiry；原子地校验并消费 refresh token。刷新不应依赖仍有效的 access token：目前 refresh 被挂在 `session.rs:48` authed_router，下次修复过期校验时必须同时调整这一协议问题。
- 验收：可控时钟覆盖到期前后、缓存开启/关闭、原始绝对期限、并发刷新、仅refresh token且access已过期；撤销与轮换回归不应退化。

## SEC-03 / P1（条件性）：OIDC 身份没有绑定 issuer/subject，用户名碰撞可登录既有账户（确认，置信度高）

- `crates/server/src/routing/client/oidc.rs:1134` 的 generate_matrix_user_id 使用 preferred_username/email 前缀 + sub，并过滤字符、转小写；未纳入 provider/issuer，prefix 是全局配置（1169）。
- `oidc.rs:1338` 的 create_or_get_user 仅按拼出的 Matrix 用户 ID 查 users（1369）；找到已有行直接用于登录，没有查询 `(issuer, sub) -> user_id` 绑定，也没有既有账户证明或显式 linking 流程。回调805行签发该用户的 SSO login token，或后续签发本地访问令牌。
- 触发条件：启用本地 OIDC，两个受信任 provider 产生相同 username/sub 组合；或 OIDC 映射 ID 恰好等于既有原生账户；或一个 provider 的不同 sub 在去字符/转小写后碰撞。例如 `preferred_username=alice, sub=a:b` 与 `sub=ab` 同时映射 alice_ab。这不是任意用户在默认配置下可直接选择 sub 的假设；实际可利用性取决于 provider 的标识规则和账号存量。
- 影响：身份跨 provider/跨原生认证方式混淆，条件满足时接管既有 Matrix 身份。用户名/email 改变还可能让同一 subject 映射到新账户。
- 建议：建立有唯一约束的 `(canonical_issuer, exact_subject)` 绑定；用户名仅用于首次分配显示友好的本地 ID，冲突生成新 ID；链接既有账户必须通过既有账户重新认证。迁移时显式审计已有绑定，不能自动依名称回填。
- 验收：同 sub 不同 issuer、相似/不同大小写 sub、相同 subject 修改 username、原生账户预占目标 ID；均不得隐式登录另一身份。

## SEC-04 / P2：远端普通媒体流没有字节总量与下载准入上限（确认实现缺口，置信度高）

- `crates/server/src/media/remote.rs:68` 非 multipart 路径直接代理 bytes_stream；只有 multipart 在73行使用 max_remote_media_size。媒体配置该字段的注释实际上限定了缓冲场景，因此这里不是“所有流都被配置承诺限制”的断言。
- `crates/server/src/config/media.rs:98` 默认 allow_legacy=true；`freeze_legacy` 仅冻结 preview_url，普通远端 download 仍可访问。已认证下载也没有全局工作准入，且通用限流对安全方法直接跳过（`crates/server/src/hoops.rs:302` 附近）。
- 影响：恶意远端配合并发下载可占用出站/入站连接和带宽；流式响应避免单请求无限缓冲，因此不将其描述为确定的单请求内存耗尽。reqwest 超时仍提供时间边界，但不等价于字节或全局并发边界。
- 建议：远端媒体全局/每源并发准入、传输字节上限、下载预算与拒绝指标；保持流式转发。根据兼容性策略默认关闭旧无鉴权远端抓取，或者对其独立限流。
- 验收：chunked 超大响应、并发多个源、断开客户端、慢响应；工作许可及时释放，资源占用受上限约束。

## 已观察到的防护与未认定为漏洞的项目

- 联邦/推送提供 DNS CIDR 过滤与 IP literal 检查、重定向检查；启动拒绝代理环境变量，明确支持边界。
- URL preview 最大16个工作许可、响应体大小和图片大小限制；thumbnail 解码尺寸/内存限制，CPU工作池隔离。
- 管理路由检查 admin；MAS共享密钥比较使用 constant-time；原生账户鉴权调用 ensure_account_usable。
- get_room_event/get_context 确实缺少路径房间与事件房间相等检查，但权限按事件实际房间校验，此处是协议一致性缺陷，不能据此声称绕过私有房间权限。
- OIDC session cookie 直接保存JSON而未签名，值得改为服务端一次性会话/完整性保护；没有证明仅修改自己Cookie即可窃取他人OAuth凭据，因此本次不单独把“明文cookie”定为已证实账号接管。
- 密码/JWT/签名路径只做抽样检查。未进行外部漏洞数据库/Cargo供应链审计，不提供“无漏洞”结论。SEC-03之外的OIDC协议ID token校验和provider发现元数据属于下一轮专项范围。
