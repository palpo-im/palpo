## 安全

### SEC01 已离房成员仍收到后续消息推送

**位置：**`crates/server/src/room.rs:248`；`crates/server/src/room/timeline.rs:461`、`:507`；`crates/server/src/sending.rs:725`；`crates/server/src/user/pusher.rs:124`、`:223`。

`get_our_real_users()` 仅按 room_id 查询 room_users，没有限定当前 join 或本服用户。`membership.rs:250`、`:276` 在 leave/ban 时保留对应成员行。后续 append 仍为这些用户计算 push actions，并为现存 pusher 排队。发送阶段只检查事件撤销、pusher 和推送规则，没有检查该事件对收件人的可见性；默认消息规则可继续返回 Notify。非 event_id_only 推送把 `event.content`、发送者和房间名直接发给推送端点。

**触发：**A 注册可接收正文的 HTTP pusher，加入私有未加密房间，随后 leave、被 kick 或 ban；B 再发新消息。A 的推送端点仍能收到新消息正文。加密房间的结论限于密文和事件元数据，不据此声称能够解密。

**修复与验收：**排队时筛选正确的本地接收者，投递时按事件及成员历史重新检查可见性，保留邀请通知的必要特例。用受控 HTTP 接收器覆盖 leave/kick/ban，以及入队后、投递前离房的交错；新消息不得发给无权接收者，正常成员和邀请通知仍工作。离房停止接收房间事件的语义见 [Matrix Leaving rooms](https://spec.matrix.org/latest/client-server-api/#leaving-rooms)。当前证据为完整静态调用链。

### SEC02 本地 OIDC 向任意目标发送登录令牌

**位置：**`crates/server/src/routing/client/oidc.rs:548`、`:813`、`:823`；标准 SSO 入口 `crates/server/src/routing/client/session.rs:1605`。

本地 OIDC 接受 redirectUrl/redirect_url，仅检查 URL 可解析，将其保存到 session。认证成功后签发短期 login token，追加 loginToken 参数并直接跳转，没有目标信任策略，也没有由 Palpo 向用户确认凭证将授予哪个客户端。标准 SSO 入口的本地 OIDC 分支同样进入此路径。

**触发：**启用本地 OIDC，攻击者诱导用户访问带攻击者 callback 的 SSO 链接；用户已有 IdP 会话时可能自动完成认证。攻击者收到令牌后可在有效期内用 m.login.token 换取登录会话。IdP 对 Palpo OAuth 应用的授权并不等于对最终接收 Matrix 凭证的客户端授权。该问题不覆盖已有 redirect allowlist 的 delegated SSO。

**修复与验收：**统一 SSO 目标校验；预置信任的精确目标可以直接放行，其余在 Palpo 明确展示目标并取得用户授权后再签发令牌。覆盖自定义和标准入口、受信任 Web 客户端及合法原生客户端流程。state、PKCE 和五秒 TTL 不能替代目标授权。[Matrix SSO security considerations](https://spec.matrix.org/latest/client-server-api/#security-considerations-15) 明确讨论这种恶意客户端诱导问题及确认措施。当前证据为完整静态调用链，未执行账户接管实验。

### SEC03 远端缩略图允许响应头注入

**位置：**`crates/server/src/routing/client/media.rs:320`；`crates/server/src/utils/content_disposition.rs:111`；公开入口 `crates/server/src/routing/media.rs:48`。

远端缩略图分支执行 `*res.headers_mut() = response.headers().clone()`。后续 apply_download_headers 只重设 Content-Type、Content-Disposition 和 nosniff，未剥除 Set-Cookie、Refresh、Access-Control-* 等不可信响应策略。普通远端下载已通过 media/remote.rs 的响应头白名单收紧，缩略图分支遗漏。legacy thumbnail 在默认 allow_legacy=true 时公开可达。

**触发：**允许访问的恶意公网联邦服务器返回小图片及 Set-Cookie；浏览器访问 Palpo 对应的 legacy thumbnail URL 后，看到的是 Palpo 域的响应，Cookie 可按该域存储。Cookie 处理依据 [RFC 6265 section 5.3](https://httpwg.org/specs/rfc6265.html#section-5.3)。本项仅确认同源响应头及 Cookie 注入，不声称已证明账户接管。

**修复与验收：**复用普通下载的允许列表，剥除认证、Cookie、跳转和跨域策略头。受控真实 HTTP peer 返回图片与恶意头，断言正文正确、安全下载头保留、其余头剥除。当前证据为静态响应传递链。

### SEC04 非成员可注入私有房间公开回执

**位置：**`crates/server/src/routing/client/room/receipt.rs:34`；`crates/server/src/event.rs:88`；`crates/server/src/room/receipt.rs:21`、`:61`；`crates/server/src/sync_v3.rs:921`。

send_receipt 直接按 event_id 全局查询 event_sn，未验证调用者对目标房间的授权，也不验证事件属于目标房间。update_read 以路径中的 room_id、认证用户和查到的事件组合写回执，随后向目标房间联邦参与者广播；房间成员的 sync 会读到这些公开回执。

**触发：**A 从未加入私有房间 R，但知道其 room ID；A 在自己的房间 S 创建 E，再对 `/rooms/R/receipt/m.read/E` 提交 `{}`，即可把外房间事件的回执写入 R。无需知道 R 的任何事件。本项是越权写入和关联完整性破坏，不声称可以读取 R 的正文。

**修复与验收：**所有回执入口统一核验用户授权、事件所属房间和事件可见性后再写库或广播。覆盖非成员、离房、ban 和同一已加入用户提交外房间事件；失败后不能留下回执、联邦 EDU 或通知状态变更。当前证据为完整静态调用链。

## Matrix 协议与通知语义

### MX01 旧 fully-read 标记删除更晚消息的通知

**位置：**`crates/server/src/routing/client/room.rs:425`；`crates/server/src/routing/client/room/receipt.rs:50`；`crates/server/src/room/push_action.rs:182`。

read_markers 收到 m.fully_read 后调用 remove_actions_for_room，删除该用户在整个房间的全部 push actions，没有事件位置限制。若同一请求带 m.read，后续 summary 重算会根据已清空的 actions 将更晚的真实未读消息也计为零。receipt/m.fully_read 入口同样删除全房通知。

**触发：**房间按顺序产生 A、B、C，B/C 未读；客户端发送 `{"m.fully_read":"$A","m.read":"$A"}`，B/C 的 actions 被删且计数归零。新消息在客户端提交旧阅读位置前到达即可触发，不需要恶意输入。

**修复与验收：**fully-read 维护对应 account data，通知处理与 read receipt 的覆盖范围保持一致，绝不能删除标记之后的通知。两个入口和仅带 m.fully_read 的情况均需回归。[Fully read markers](https://spec.matrix.org/v1.12/client-server-api/#fully-read-markers) 与 [Marking notifications as read](https://spec.matrix.org/latest/client-server-api/#marking-notifications-as-read) 定义了两者的区别。证据为静态删除范围及后续重算路径。

### MX02 main 回执误清其他线程通知

**位置：**`crates/server/src/routing/client/room/receipt.rs:29`；`crates/server/src/room/push_action.rs:169`。

handler 只把 ReceiptThread::Thread(id) 转成 Some(id)，Main 和 Unthreaded 都转成 None。remove_actions_until(None) 不加线程过滤，删除全房各线程中 event_sn 不大于目标事件的 actions。

**触发：**支线 T 有未读回复 R，随后主时间线产生 M；对 M 提交 `{"thread_id":"main"}` 后，R 的通知也被清除。公开和私有 read receipt 都受影响。

**修复与验收：**清理函数保留 Unthreaded、Main、Thread(id) 三种作用域；Main 对应主时间线，Unthreaded 才允许覆盖所有线程。分别检查三个作用域的边界。[Threaded read receipts](https://spec.matrix.org/latest/client-server-api/#threaded-read-receipts)。已做选择条件的算法演示，未做 Palpo HTTP 回归。

### MX03 私有线程回执丢失作用域

**位置：**`crates/server/src/routing/client/room/receipt.rs:83`；`crates/data/src/room/receipt.rs:82`、`:24`；`crates/server/src/room/receipt.rs:92`。

m.read.private 分支未向 set_private_read 传 body.thread，固定写 thread_id=None、json_data=null。读取时按 JSON thread_id 的 DISTINCT ON 去重，因此同一用户不同线程的私有回执落到同一个空作用域，只保留最新一条，并在默认解码时成为 unthreaded。Sliding Sync 的额外私有回执构造也固定为 unthreaded。

**触发与验收：**同一用户在 T1/T2 各提交一个私有回执，由其另一设备执行初始及增量 sync；应保留两个独立线程位置，同时保持其他用户无法收到私有回执。修复应持久化完整 Receipt 的时间与作用域，并统一两个同步实现。[Receipts](https://spec.matrix.org/v1.12/client-server-api/#receipts)。证据为写入、去重和同步调用链，并做过空作用域合并的算法演示。

### MX04 联邦公开线程回执被改为 unthreaded

**位置：**`crates/server/src/room/receipt.rs:55`；`crates/core/src/events/receipt.rs:106`；`crates/server/src/sending.rs:337`。

update_read 本地保存公开回执时保留线程 JSON，但直接构造外发 EDU 时重新调用 Receipt::new(now)，其作用域固定为 Unthreaded。Main 或 Thread(id) 回执因此额外向远端发布一个全房间阅读位置。发送 selector 之后补发正确线程回执也不能撤销已更新的独立 unthreaded 位置。

**修复与验收：**外发 EDU 复用原作用域；按线格式约束组织多作用域数据。两服务器夹具分别提交 Main 和 Thread(id) 回执，记录真实 /send 事务，断言没有从该请求衍生的无 thread_id 回执。[Federation receipts](https://spec.matrix.org/v1.12/server-server-api/#receipts)。当前证据为构造与序列化调用链。

### MX05 missing-events 忽略深度且返回重复祖先

**位置：**`crates/server/src/routing/federation/event.rs:145`、`:175`。

handler 不读取请求的 min_depth，无法保证请求的最低深度；遍历 prev_events 又没有 visited/queued 集合。共同祖先会重复入队、重复返回并消耗 limit，使唯一缺失事件被挤出。

**触发：**`L→{P,Q}`、`P→C`、`Q→C`、`C→D`，latest_events=[L]、limit=4；当前算法输出 `[C,C,Q,P]`，四个结果只有三个唯一事件，D 被重复 C 挤出。独立的线性链与非零 min_depth 可验证深度边界。

**修复与验收：**按唯一事件遍历和计数，执行深度边界，并保留已有房间及历史可见性检查。[get_missing_events](https://spec.matrix.org/latest/server-server-api/#post_matrixfederationv1get_missing_eventsroomid) 定义 BFS、limit 和 min_depth。已执行源码关联的 diamond-DAG 算法演示；未执行真实联邦互操作测试。

## 性能与并发

### CP01 显式订阅可以无限扩大时间线读取

**位置：**`crates/server/src/sync_v5.rs:1268`、`:1347`、`:1362`；`crates/server/src/sync_v3.rs:1426`、`:1443`；`crates/server/src/room/timeline/stream.rs:243`、`:254`。

RoomSubscription.timeline_limit 为无约束 i64，fetch_subscriptions 直接转 usize；同文件列表路径在 1192 行却限制为最多 100。订阅值直接传给 load_timeline，后者使用 limit+1，SQL 按此 LIMIT 一次 load 事件标识向量，正文虽按 256 个预取，最终仍累积整个响应。

**触发：**已加入大房间的用户设置 timeline_limit=2147483647，一次请求可使查询结果、内存及响应体随全部历史增长。负数还引入符号转换：64 位下 -1 转为 usize::MAX，后续 +1 在 debug 溢出、release 回绕；其他负数可成为极大的读取额度。

**修复与验收：**拒绝负数，列表与显式订阅采用同一服务端上限，下层也保留总量边界及安全算术。以千条以上消息比较 list/subscription 的 limit=1000，并覆盖 -1、-2、i64::MAX。当前为静态调用链与容量推断，未测实际峰值内存或吞吐。

### CP02 required_state 逐事件重写完整缓存

**位置：**`crates/server/src/sync_v5.rs:1523`、`:2076`、`:599`、`:605`、`:539`、`:561`。

请求 `["m.room.member","*"]` 时，每个新状态事件都 await mark_required_state_sent。它只插入一个 event_sn，却在连接写锁内 clone 整个 SlidingSyncCache、完整序列化，并 UPDATE 整列 JSONB。N 个成员状态至少产生 N 次串行连接 UPDATE；集合从 1 增至 N，累计复制及序列化的状态项为 1+…+N，即 Θ(N²)。sticky 请求及其他缓存也随之重复复制。该集合还持续保留历史 sn，活跃连接不触发连接过期回收。

**修复与验收：**请求内收集已发送状态，在响应构造结束时批量持久化；清理被替换状态和已退订房间的记录。用 100/1000/10000 成员夹具测 UPDATE 次数、总序列化字节和延迟，保留多实例 CAS/重试正确性。本项是复杂度推导，没有声称未经测量的耗时或提升比例。

### CP03 永远无法过期的孤儿连接缓存

**位置：**`crates/core/src/client/sync_events/v5.rs:109`；`crates/server/src/sync_v5.rs:397`、`:477`、`:626`。

conn_id 的最多 16 字符仅写在注释，没有运行时校验。请求先将 key 放入无上限 CONNECTIONS，再持久化；INSERT 失败仅警告并继续使用内存。清理只删除数据库中过期行对应的内存 key，从未成功落库的 key 没有本地时间戳，永远不会进入清理集合。

**已执行的数据库前提验证：**在独立 PostgreSQL 18 用 TEMP TABLE 复制三列 TEXT 主键，以 `SELECT string_agg(md5(i::text), '') FROM generate_series(1,200) i` 生成 6400 字节低可压缩 conn_id，插入导致 SQLSTATE 54000，`index row size 6440 exceeds btree version 4 maximum 2704`，拒绝插入后行数为 0。只使用临时表，连接结束即清除。此验证结合 Palpo 静态生命周期，确认了“有内存项、无数据库行”的可达原因；未执行 Palpo HTTP 端到端测试。

**触发与修复：**有效设备不断使用不同超长 conn_id 可累积孤儿内存项；数据库首次 INSERT 故障也会留下同类项。强制长度、每设备及全局容量，内存独立维护 last-access/TTL；落库失败也必须可淘汰。用首次写入失败和推进过期时间的回归检查清理，不能只测试正常落库的连接。

### CP04 通知汇总重算与增量更新竞态

**位置：**`crates/server/src/room/timeline.rs:501`、`:731`；`crates/server/src/room/push_action.rs:50`、`:289`、`:312`；`crates/server/src/routing/client/room/receipt.rs:99`。

append 先插入 event_push_actions，稍后才给 summary 加一。收据重算通过独立 SELECT count 再绝对值 UPDATE summary。这些 data::db 操作各自提交；append 的协调 advisory fence 没把它们纳入同一事务，收据路径也不获取该 fence。

**确定交错：**A 插入新消息 action 后暂停；B 对较老消息提交回执，重算剩余 action 并写 summary=1；A 恢复 +1，得到 2，但只有一个实际未读 action。反向交错还可能用旧 count 覆盖新增长量。v3/v5 都读取该 summary，徽标会漂移。

**修复与验收：**统一 action 变更和 summary 维护的事务、锁序或结算水位；只把重算的 SELECT/UPDATE 放进普通事务仍不足以避免重复结算。用 barrier 固定 INSERT→收据重算→increment，以及 count→新消息增量→绝对 UPDATE 两种时序，逐项比较 notify/highlight 真实 action 数。当前为静态交错证明，未执行 Palpo 并发故障注入。

## 管理接口与功能正确性

### ENG01 v3 用户列表使用错误的停用筛选参数

**位置：**`crates/server/src/routing/admin/user_admin.rs:519`、`:529`；数据过滤 `crates/data/src/user.rs:1367`。

`/_synapse/admin/v3/users` 提取 not_deactivated 并取反，却没有提取契约中的 deactivated。标准管理客户端发送 `?deactivated=true` 或 false 时，这个参数被忽略，数据层得到 None，返回所有停用状态。v2 也直接复用了数据层“true=只返回停用”的语义，而其契约是“true=包含停用、默认排除”。这会使停用账户筛选和管理统计失真。

**修复与验收：**在接口层分别实现 v2 的包含开关和 v3 的三态过滤；如需保留自定义 not_deactivated，应作为显式兼容别名处理。准备一个活跃和一个停用本地账号，分别检查两个版本的缺省、true、false 三种请求。官方契约见 [Synapse List Accounts V2 and V3](https://element-hq.github.io/synapse/latest/admin_api/user_admin_api.html#list-accounts-v3)。本项属于 Synapse 管理兼容层，不计为 Matrix 核心协议不符合。证据为参数提取与 SQL 过滤调用链。

### ENG02 大 limit 令用户列表提前丢失下一页

**位置：**`crates/server/src/routing/admin/user_admin.rs:325`、`:354`；`crates/data/src/user.rs:1438`。

数据层把 limit 裁剪到最多 1000，build_users_list 却仍用客户端原始 limit 判断是否有下一页。有 1500 个用户时请求 limit=1001，实际返回 1000 条，因 1000<1001 不返回 next_token，按分页协议遍历的工具会把剩余用户误判为不存在。

**修复与验收：**统一有效 limit，结合 from、实际返回数量和 total 计算 next_token，并验证非正 limit。以 1500 个用户、limit=1001 或 2000 检查可遍历全部唯一用户；同时覆盖恰好一页和空尾页。分页契约明确无 next_token 即无后续用户：[Synapse List Accounts](https://element-hq.github.io/synapse/latest/admin_api/user_admin_api.html#list-accounts-v2)。当前为静态边界推导，未执行对应 HTTP 夹具。

### ENG03 管理及 MAS 修改资料缺少成员状态传播

**位置：**`crates/server/src/routing/admin/user_admin.rs:420`、`:435`；`crates/server/src/routing/admin/mas.rs:318`、`:326`；对照 `crates/server/src/routing/client/profile.rs:477`、`:515`、`:526`。

管理 PUT 和 MAS set/unset_displayname 直接调用 data 层 global profile setter 后返回。setter 只修改全局 profile 并记录 profile change stream；没有生成每个已加入房间的 m.room.member，也不 refresh_presence_for_profile。普通客户端资料接口则明确执行这两步。

**触发：**用户已加入房间，管理员或 MAS 将其昵称从 Old 改为 New。全局 profile GET 和部分扩展 profile stream 可见 New，房间 m.room.member 及常规成员同步仍为 Old，远端服务器也收不到对应成员变更；头像管理更新同理。不能把全局 change stream 当作房间成员事件的替代。

**修复与验收：**提取共用的资料更新及传播服务供 client/admin/MAS 调用，保留授权入口差异，并定义部分房间传播失败的恢复方式。两个本地用户及远端成员夹具验证全局 GET、当前成员 state、增量 sync 和联邦事件一致；覆盖 MAS 删除昵称。[Events on Change of Profile Information](https://spec.matrix.org/latest/client-server-api/#events-on-change-of-profile-information) 描述自动成员及 presence 传播。当前为静态调用链对比。
